## Decision

PayMe will ship a `MockPayShapPaymentProvider` first that simulates the full
PayShap **request-to-pay** UX end-to-end without any external dependency.
The real integration via Stitch (or another aggregator) is treated as a
swappable follow-up — selected by `payme.payshap.mode=mock|stitch` in
configuration.

The mock:
- Generates a synthetic ProxyID (phone-number shaped) at checkout time.
- Renders a "request sent — approve in your banking app" screen with a QR
  code containing the ProxyID + amount.
- Exposes an "I have approved" button that POSTs to the existing
  `/webhooks/PAYSHAP` endpoint to simulate the bank confirming the payment.

The mock implements `PaymentProvider` like every other adapter, so the rest
of the system (command handler, event flow, SSE updates, audit trail) is
exercised exactly as it will be in production.

## Context

PayMe is not a bank and cannot participate in PayShap directly. Real
integrations require an aggregator: Stitch, Ozow, or Peach Payments. Standing
up sandbox credentials for any of these takes days of paperwork — and PayMe
does not have them today.

If we wait for real credentials before shipping anything, the multi-rail
demo (the whole point of this initiative) is blocked indefinitely. If
instead we model the *flow* faithfully behind the existing
`PaymentProvider` port, we can:

1. Prove the registry (ARCH-001) actually supports a second rail.
2. Drive the SSE pay page (ARCH-002) end-to-end with a payment that is
   visibly different from PayFast.
3. Swap in a real provider later by writing one new adapter class — zero
   changes to controllers, command handlers, events, or the pay page.

The mock is **not throwaway**. It stays in the repo as a development and
test fixture, behind a configuration flag, even after the real adapter
lands. This is the same role our existing `FakePaymentProvider` plays.

## Alternatives Considered

### Wait for real Stitch sandbox credentials, build the real adapter first
**Rejected.** Hard dependency on an external onboarding process. Blocks the
entire scope. Provides no learning we cannot get from a faithful mock.

### Skip PayShap entirely, demo with PayFast only
**Rejected.** The whole product story is "one PayMe link, multiple SA rails."
Without a second rail, the registry (ARCH-001) is dead weight and the SSE
demo (ARCH-002) is just "a pay page that updates" — it loses the local-rail
differentiator.

### Build against PayFast's PayShap method (PayFast now supports PayShap as a payment option)
**Considered.** Cleaner than mock-first because it uses real money. Rejected
because PayFast-routed PayShap goes through the PayFast checkout, so from
PayMe's point of view it is *still* a PayFast payment — it does not exercise
a second adapter path. We can add it later as a PayFast checkout option,
which is orthogonal to this decision.

### Use Ozow or Peach instead of Stitch as the eventual real provider
**Deferred.** All three expose REST + webhook patterns that fit the
`PaymentProvider` port. The mock-first approach makes this choice
postpone-able: pick whichever is fastest to get sandbox access for when the
time comes.

## Tradeoffs Accepted

- The mock cannot validate signatures or handle real bank failure modes.
  Acceptable — those are provider-specific concerns owned by the eventual
  real adapter, not by the rest of the system.
- We must be careful never to register the mock under `PAYSHAP` in
  production. Mitigation: the bean is only created when
  `payme.payshap.mode=mock`, and production config sets it to `stitch`.
- The "approve" button is a security non-event in dev but would be a
  catastrophic backdoor in prod. Mitigation: same as above — the mock
  controller is only registered when `payme.payshap.mode=mock`.

## Revisit When

- Stitch (or chosen aggregator) sandbox credentials are obtained — at that
  point, write `StitchPayShapPaymentProvider` and flip the default mode to
  `stitch` in the staging environment.
- A merchant requests a different aggregator (Ozow / Peach) — write a
  parallel adapter and let the registry resolve by configuration.
- PayShap rules change in a way the mock no longer faithfully represents
  (e.g. the request-to-pay UX moves to a different model) — update the mock
  so it remains accurate for development.
